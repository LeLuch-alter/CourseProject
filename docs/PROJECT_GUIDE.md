## 1. Что это за программа

**Kvit** (от «квиты» — «мы в расчёте») — настольное приложение для Windows, в котором человек ведёт
учёт своих долгов и кредитов:

- записывает долг: название, кому должен, сумму, срок, примечание;
- вносит платежи по долгам;
- видит, сколько уже оплачено, сколько осталось, что просрочено;
- смотрит отчёты, календарь сроков, прогноз погашения;
- экспортирует данные в Excel (CSV).

Важные границы (их стоит проговаривать на защите):

- Программа **не подключается к банкам** и другим сервисам. Все данные вводит пользователь.
- Программа **не начисляет проценты и штрафы**. Ставку можно записать «для справки», но остаток —
  это всегда «сумма долга минус платежи». Так правила прозрачны и их легко проверить.
- Данные хранятся в облачной базе **Supabase** (это PostgreSQL), поэтому они не пропадут при
  переустановке программы, а каждый пользователь видит только свои записи.

## 2. Главная идея архитектуры: слои

### 2.1. Аналогия с рестораном

Представьте ресторан:

| В ресторане | В программе | Пакет |
|---|---|---|
| Зал и официант: общается с гостем, показывает меню, принимает заказ | Экраны JavaFX: показывают данные, принимают ввод | `ui` |
| Повар: знает рецепты, проверяет, что продукты свежие | Бизнес-логика: правила, проверки, расчёты | `service` |
| Кладовщик: знает, где что лежит на складе | Доступ к данным: как прочитать и записать в базу | `repository` |
| Склад | База данных Supabase | `supabase/schema.sql` |
| Продукты и блюда, которые передают друг другу | Модели: `Debt`, `Payment` и др. | `model` |

Официант не идёт сам на склад и не готовит. Повар не выходит в зал. Каждый делает своё.

Поток данных в программе всегда такой:

```
Экран (ui)  →  Сервис (service)  →  Репозиторий (repository)  →  Supabase
     ↑                                                              │
     └──────────────── модели (model) возвращаются обратно ─────────┘
```

### 2.2. Зачем это нужно — конкретно

1. **Логику можно тестировать без окна и без интернета.** `DebtCalculator` — обычный класс без
   JavaFX и без сети. В тесте мы создаём несколько объектов `Debt` и `Payment` в памяти и
   проверяем, правильно ли посчитан остаток. Если бы расчёт был внутри обработчика кнопки, его
   нельзя было бы проверить, не открывая окно.
2. **Изменения не расползаются.** Если завтра заменить Supabase на другую базу, переписывать
   придётся только `repository`. Экраны и правила не изменятся.
3. **Код легче читать.** Открыв `DebtCalculator`, вы видите только правила расчёта — без
   кнопок, цветов и HTTP-запросов.
4. **Это требование задания** (см. постановку: «Keep SQL and database access out of JavaFX
   button handlers. Keep calculations out of UI controllers»).

### 2.3. Почему не иначе

- **«Всё в одном классе»** — для 300 строк сработало бы, но у нас ~6000 строк. Найти ошибку
  в таком классе невозможно, а тестировать — тем более.
- **Spring / внедрение зависимостей** — промышленный инструмент, но для курсового проекта он
  добавляет много «магии» (аннотации, контейнер), которую сложно объяснить. Мы собираем объекты
  вручную в `App.start()` — пять строк, всё видно глазами.
- **Интерфейсы на каждый класс** (`DebtRepository` + `DebtRepositoryImpl`) — полезно в больших
  командах, но у нас одна реализация каждого класса. Лишние интерфейсы только удвоили бы
  количество файлов. Единственный интерфейс в проекте — `Page`, и он нужен по делу (см. 14.3).
- **Отдельный сервер (REST API на Java)** между программой и базой — правильнее для
  продакшена, но это второй проект. Supabase уже даёт готовый REST API и защиту на уровне
  строк (RLS), поэтому сервер не нужен.

## 3. Технологии и почему именно они

| Технология | Что делает | Почему выбрана |
|---|---|---|
| **Java 22** | Язык программы | Требование задания; установлен на компьютере; даёт `record`, `switch`-выражения, Foreign Function API |
| **JavaFX 22** | Окна, кнопки, таблицы, анимации | Требование задания; современнее Swing; есть CSS для оформления |
| **Maven** + `mvnw` | Сборка, зависимости, запуск | Стандарт для Java; `mvnw` (wrapper) сам скачивает нужный Maven — ничего ставить не надо |
| **Supabase** | PostgreSQL + вход пользователей + REST API | Требование задания; бесплатно; даёт Auth и RLS из коробки |
| **Jackson** | Превращает JSON в объекты Java и обратно | Supabase отвечает в формате JSON; Jackson — самая распространённая библиотека |
| **JUnit 5** | Автоматические тесты | Стандарт для Java |

### 3.1. Почему не прямое подключение к PostgreSQL (JDBC)

Это главный архитектурный вопрос проекта, и на защите его почти наверняка зададут.

С JDBC программа подключалась бы к базе **логином и паролем базы данных**. Этот пароль пришлось бы
положить внутрь программы. Но программу отдают пользователям, а любой пользователь может открыть
`.jar`-файл и достать из него строки. С паролем базы он получил бы доступ **ко всем данным всех
пользователей**.

Поэтому мы делаем иначе:

1. Программа знает только **publishable key** — открытый ключ, который сам по себе **не даёт
   доступа к таблицам**. Его не страшно «потерять».
2. Пользователь **входит по email и паролю** через Supabase Auth и получает **токен** — временный
   пропуск, подписанный сервером.
3. Каждый запрос к данным идёт с этим токеном. База сама определяет, чей это токен, и по
   правилам **RLS** (Row Level Security) показывает только строки этого пользователя.

Итог: даже если кто-то вытащит ключ из программы, без своего логина он ничего не увидит, а со своим
логином увидит только свои данные.

### 3.2. Почему UI написан кодом, а не в FXML

В JavaFX экраны можно описывать в XML-файлах (FXML) и рисовать в Scene Builder. Мы пишем экраны
кодом на Java, потому что:

- всё в одном месте: открыл `DebtsView.java` — видишь и вид, и поведение;
- экраны у нас динамические (таблица меняет содержимое, календарь строит сетку, карточка долга
  собирается из данных) — в коде это проще, чем в XML;
- не нужен механизм рефлексии, который требует FXML.

Минус: нет визуального редактора. Для курсового проекта это не критично.


### 4.1. Почему пакет называется `kz.kvit`

В Java принято называть пакеты «перевёрнутым доменом»: `kz` — страна, `kvit` — название продукта.
Так имена классов не пересекаются с чужими библиотеками (у Jackson, например, `com.fasterxml...`).

### 4.2. Почему `src/main/java` и `src/main/resources` разделены

Это соглашение Maven. В `java` — код, который компилируется. В `resources` — файлы, которые
копируются в программу как есть (CSS, картинки, тексты). Благодаря соглашению Maven не нужно
ничего настраивать: он сам знает, где что лежит. Папка `src/test/java` — тесты; они не попадают
в готовую программу.

### 4.3. Почему ресурсы лежат в `kz/kvit/ui/...`

Чтобы класс мог найти файл по короткому пути. В `App.java`:

```java
getClass().getResource("ui/styles.css")
```

`App` находится в пакете `kz.kvit`, поэтому путь `ui/styles.css` ищется как
`kz/kvit/ui/styles.css` — ровно там, где лежит файл.

## 5. Запуск программы: от main до окна

Команда `.\mvnw.cmd javafx:run` делает три вещи: компилирует код, копирует ресурсы и запускает
класс `kz.kvit.App` (он указан в `pom.xml` в плагине `javafx-maven-plugin`).

### 5.1. `App.main` → `launch` → `start`

```java
public static void main(String[] args) {
    launch(args);
}
```

`launch` — метод JavaFX. Он запускает «движок» JavaFX, создаёт главное окно (`Stage`) и вызывает
наш метод `start(Stage stage)`. Всё, что связано с окном, происходит внутри `start` и позже — на
специальном потоке **JavaFX Application Thread** (о потоках — в 13.4).

### 5.2. Что делает `start` по шагам

```java
applySettings();                         // 1. язык и тема из сохранённых настроек
config = AppConfig.load();               // 2. URL и ключ Supabase из config.properties
SupabaseClient client = new SupabaseClient(config);                       // 3. клиент сети
authService = new AuthService(client);                                    // 4. сервис входа
debtService = new DebtService(new DebtRepository(client),
                              new PaymentRepository(client));             // 5. сервис долгов
stage.setTitle(Brand.NAME);              // 6. заголовок, минимальный размер окна
showLogin();                             // 7. первый экран — вход
stage.getIcons().add(Brand.windowIcon(stage.getScene()));                 // 8. иконка окна
stage.show();                            // 9. показать окно
WindowsIntegration.applyTitleBar(stage, Theme.current().isDark());        // 10. цвет заголовка
```

Обратите внимание на шаги 3–5. Это и есть «ручное внедрение зависимостей»: мы **один раз**
создаём объекты и передаём их друг другу через конструкторы. Один `SupabaseClient` используется
и для входа, и для данных — поэтому токен, полученный при входе, автоматически используется для
запросов к таблицам.

Если `config.properties` не найден или в нём ошибка, `AppConfig.load()` бросает
`IllegalStateException`, и мы показываем понятное окно с ошибкой вместо падения программы.

### 5.3. Переключение экранов

```java
private void showLogin(String message) {
    mainView = null;
    setContent(new LoginView(authService, settings, message, () -> showMain(0), this::reloadUi).getRoot());
}

private void showMain(int section) {
    mainView = new MainView(authService, debtService, settings, section, this::showLogin, this::reloadUi);
    setContent(mainView.getRoot());
}
```

Экраны не знают друг о друге. `LoginView` не создаёт `MainView` — он просто вызывает
переданную ему функцию `onSignedIn` (здесь `() -> showMain(0)`). Решает, *что* показать дальше,
только `App`. Это называется **обратный вызов (callback)** и избавляет экраны от взаимных
зависимостей.

`this::showLogin` — ссылка на метод. Это короткая запись лямбды `message -> showLogin(message)`.

### 5.4. Смена темы и языка: «просто пересобрать экран»

```java
private void reloadUi() {
    applySettings();
    if (mainView != null) {
        showMain(mainView.getSelectedSection());
    } else {
        showLogin();
    }
    WindowsIntegration.applyTitleBar(stage, Theme.current().isDark());
}
```

Когда пользователь меняет язык, можно было бы пройти по всем надписям и поменять текст. Но это
сотни мест и легко что-то забыть. Мы делаем проще: сохраняем выбор, **создаём экран заново** —
он сам возьмёт тексты на новом языке — и открываем тот же раздел (`getSelectedSection()`).

### 5.5. Темы: два CSS-файла

```java
scene.getStylesheets().setAll(getClass().getResource("ui/styles.css").toExternalForm());
if (!Theme.current().isDark()) {
    scene.getStylesheets().add(getClass().getResource("ui/theme-light.css").toExternalForm());
}
```

`styles.css` описывает всё оформление и тёмные цвета. `theme-light.css` подключается **поверх** и
переопределяет только цвета. Почему отдельным файлом, а не классом на корневом элементе — см. 15.3.

### 5.6. «Системная» тема следит за Windows

```java
Platform.getPreferences().colorSchemeProperty().addListener((obs, oldScheme, newScheme) -> {
    if (settings.getTheme() == UserSettings.ThemeChoice.SYSTEM) {
        reloadUi();
    }
});
```

`colorSchemeProperty()` — «наблюдаемое свойство» JavaFX: когда в Windows переключают светлый/тёмный
режим, JavaFX вызывает наш слушатель, и если выбрана «Как в системе», мы пересобираем экран.

## 6. База данных: `supabase/schema.sql`

Скрипт выполняется один раз в Supabase → SQL Editor. Он создаёт всё, что нужно в базе.

### 6.1. Таблица `debts`

```sql
create table public.debts (
    id              bigint generated always as identity primary key,
    user_id         uuid not null default auth.uid() references auth.users (id) on delete cascade,
    title           text not null check (char_length(btrim(title)) between 1 and 200),
    creditor_name   text not null check (char_length(btrim(creditor_name)) between 1 and 200),
    original_amount numeric(14, 2) not null check (original_amount > 0),
    interest_rate   numeric(5, 2) check (interest_rate between 0 and 100),
    created_at      timestamptz not null default now(),
    due_date        date,
    status          text not null default 'ACTIVE' check (status in ('ACTIVE', 'PAID', 'CANCELLED')),
    notes           text check (char_length(notes) <= 1000)
);
```

Разберём каждое решение:

- **`bigint generated always as identity`** — база сама выдаёт номера 1, 2, 3… Программа никогда
  не придумывает `id` сама — так не будет двух одинаковых.
- **`user_id ... default auth.uid()`** — ключевая строка безопасности. `auth.uid()` — функция
  Supabase, которая возвращает id пользователя **из токена текущего запроса**. Программа вообще не
  отправляет `user_id` — база ставит его сама. Поэтому невозможно «подделать» владельца и записать
  долг на чужой аккаунт.
- **`references auth.users (id) on delete cascade`** — внешний ключ: `user_id` обязан
  существовать среди пользователей. Если пользователя удалят, удалятся и его долги.
- **`numeric(14, 2)`** — точное десятичное число: до 14 цифр, из них 2 после запятой. **Не**
  `float`/`double`: они хранят числа в двоичном виде, и `0.1 + 0.2` там равно `0.30000000000000004`.
  Для денег это недопустимо. В Java этому типу соответствует `BigDecimal`.
- **`check (...)`** — ограничения. База **сама** откажется сохранить отрицательную сумму, пустое
  название или неизвестный статус. Даже если в программе будет ошибка, мусор в базу не попадёт.
- **`timestamptz`** — дата-время с часовым поясом (когда создана запись). **`date`** — просто дата
  без времени (срок погашения): времени у срока нет.
- **`status` как текст с `check`**, а не отдельная таблица статусов — статусов всего три, и они
  не меняются. Отдельная таблица была бы излишней.

### 6.2. Таблица `payments`

```sql
create table public.payments (
    id           bigint generated always as identity primary key,
    debt_id      bigint not null references public.debts (id) on delete cascade,
    amount       numeric(14, 2) not null check (amount > 0),
    payment_date date not null default current_date,
    notes        text check (char_length(notes) <= 1000),
    created_at   timestamptz not null default now()
);
```

- **`debt_id ... references debts(id)`** — платёж обязан принадлежать существующему долгу
  (требование задания: «Each payment must reference an existing debt»).
- **`on delete cascade`** — удалили долг → удалились его платежи. Иначе остались бы «платежи-сироты».
- **Почему нет `user_id` в платежах?** Владелец платежа = владелец его долга. Хранить это дважды —
  значит рисковать, что когда-то значения разойдутся. Правила доступа к платежам смотрят на долг
  (см. 6.5).
- **Почему мы не храним «оплачено» и «остаток» в таблице долгов?** Это производные значения:
  их всегда можно посчитать из платежей. Если бы мы их хранили, нужно было бы следить, чтобы при
  каждом добавлении/удалении платежа они обновлялись, — и любая ошибка дала бы неверный остаток.
  Задание прямо об этом говорит: «Store individual payment records and calculate totals from them».

### 6.3. Индексы

```sql
create index debts_user_id_idx on public.debts (user_id);
create index payments_debt_id_idx on public.payments (debt_id);
```

Индекс — как алфавитный указатель в книге: база находит «все долги пользователя X» без
просмотра всей таблицы. Мы ищем именно по этим полям — поэтому индексы на них.

### 6.4. Триггеры: защита правил прямо в базе

**Триггер** — функция, которую база сама вызывает перед/после изменения строки.

**`check_payment_within_balance`** — «сумма платежей не может превысить долг»:

```sql
select original_amount into debt_amount
from public.debts
where id = new.debt_id
for update;
```

- `new` — платёж, который сейчас пытаются сохранить.
- `for update` — **блокировка строки долга** до конца транзакции. Зачем? Представьте: остаток
  1000 ₸, и в одну и ту же секунду приходят два платежа по 800 ₸ (например, двойной клик). Без
  блокировки оба увидят «остаток 1000» и оба пройдут — итого 1600. С блокировкой второй
  платёж ждёт, пока первый закончится, видит уже «остаток 200» и отклоняется. Это защита от
  **состояния гонки** (race condition).

Затем считается сумма уже внесённых платежей, и если вместе с новым она больше долга —
`raise exception` отменяет сохранение.

**`check_debt_amount_covers_payments`** — «нельзя уменьшить сумму долга ниже уже оплаченного».

Зачем дублировать проверки, если они есть в Java (`DebtValidator`)? Потому что к REST API
Supabase можно обратиться в обход программы (например, через Postman со своим токеном). Проверки
в Java — для удобства (понятное сообщение сразу), проверки в базе — для **гарантии**.

`set search_path = ''` в функциях — мера безопасности: функция обращается к таблицам только по
полному имени (`public.debts`), и злоумышленник не может подсунуть свою таблицу с таким же
именем в другой схеме.

### 6.5. Права и Row Level Security (RLS)

```sql
revoke all on public.debts, public.payments from anon, public;
grant select, insert, update, delete on public.debts, public.payments to authenticated;
```

- `anon` — роль «не вошёл в систему». У неё **нет никаких прав** на наши таблицы.
- `authenticated` — роль «вошёл». Ей можно читать и писать… но только то, что разрешат политики.

```sql
alter table public.debts enable row level security;

create policy "Users read own debts" on public.debts
    for select to authenticated
    using (user_id = (select auth.uid()));
```

**RLS** — это фильтр, который база **сама** добавляет к каждому запросу. Когда программа просит
«дай все долги» (`GET /rest/v1/debts`), база мысленно дописывает `where user_id = <id из токена>`.
Поэтому в Java-коде нет ни одного `where user_id = ...` — это делает база, и забыть это невозможно.

- `using (...)` — какие **существующие** строки видно/можно менять/удалять.
- `with check (...)` — какие **новые** значения разрешено записать (нельзя, например, изменить
  `user_id` на чужой).
- `(select auth.uid())` в скобках с `select` — рекомендация Supabase для скорости: функция
  вычисляется один раз на запрос, а не для каждой строки.

Для платежей политики проверяют владельца через долг:

```sql
using (exists (select 1 from public.debts d
               where d.id = payments.debt_id and d.user_id = (select auth.uid())))
```

«Платёж виден, если существует долг с этим `debt_id`, который принадлежит текущему пользователю».

### 6.6. `sample_data.sql`

Блок `do $$ ... $$` — анонимная процедура на языке PL/pgSQL. Он находит пользователя по email и
создаёт четыре долга с платежами. Выполняется в SQL Editor от имени администратора, поэтому
RLS не мешает, а `user_id` указывается явно. Даты относительные (`current_date + 120`), чтобы
демонстрация всегда выглядела «свежо»: есть и просроченный долг, и долг со сроком в будущем.

## 7. Безопасность целиком

Сведём всё вместе — это удобно рассказать на защите одним блоком.

| Угроза | Защита | Где |
|---|---|---|
| Кто-то достал ключ из программы | В программе только publishable key, он не даёт доступа к таблицам без входа | `config.properties`, `schema.sql` |
| Разработчик по ошибке вставил секретный ключ | Программа откажется запускаться | `AppConfig.isSecretKey` |
| Пользователь хочет увидеть чужие данные | RLS: база отдаёт только строки владельца токена | `schema.sql` |
| Пользователь подделывает `user_id` | `user_id` заполняет база из токена; `with check` запрещает менять | `schema.sql` |
| Некорректные данные (отрицательная сумма и т.п.) | Проверка в Java + `check`-ограничения в базе | `DebtValidator`, `schema.sql` |
| Переплата / гонка двух платежей | Триггер с `for update` | `schema.sql` |
| SQL-инъекция | SQL не пишется вообще; в URL попадают только числа (`id`), текст идёт в теле JSON | репозитории |
| Ключ попал в Git | `config.properties` в `.gitignore` | `.gitignore` |
| Пароль остался в памяти/на диске | Пароль не сохраняется; поле очищается после входа; токены только в памяти | `LoginView`, `SupabaseClient` |
| Компьютер оставили без присмотра | Автовыход через 15 минут бездействия | `MainView.startIdleWatch` |
| Перехват трафика | Только HTTPS (`AppConfig` проверяет `https://`) | `AppConfig` |

Честные ограничения (лучше назвать их самим):

- publishable key можно извлечь — поэтому защита держится на входе и RLS, а не на секретности ключа;
- защиты от подбора пароля в самой программе нет (Supabase ограничивает частоту попыток);
- профессионального аудита безопасности не было.

## 8. Слой данных: `repository`

### 8.1. `SupabaseClient` — всё общение с сервером

Это единственный класс, который знает про HTTP. Остальной код просто вызывает
`client.get("/rest/v1/debts?...")` и получает JSON.

**Поля:**

```java
private final HttpClient httpClient;   // встроенный в Java HTTP-клиент (java.net.http)
private final ObjectMapper mapper;     // Jackson: JSON ⇄ Java
private Session session;               // токены текущего пользователя (или null)

private record Session(String accessToken, String refreshToken, Instant expiresAt, String email) {}
```

`Session` — `record` (неизменяемый «контейнер данных», см. 9.2). Токены хранятся **только в
памяти**: после закрытия программы их нет, войти нужно заново. Это безопаснее, чем сохранять их
на диск.

**Настройка Jackson:**

```java
JsonMapper.builder()
    .enable(DeserializationFeature.USE_BIG_DECIMAL_FOR_FLOATS)
    .enable(StreamWriteFeature.WRITE_BIGDECIMAL_AS_PLAIN)
```

- Первая опция: числа с дробной частью из JSON читать как `BigDecimal`, а не `double`
  (иначе 0.1 превратилось бы в 0.1000000000000000055…).
- Вторая: писать `BigDecimal` обычной записью (`1500.50`), а не научной (`1.5005E+3`).

**Вход:**

```java
public synchronized void signIn(String email, String password) {
    ObjectNode body = createObject().put("email", email).put("password", password);
    session = toSession(send(authRequest("/auth/v1/token?grant_type=password", body)));
}
```

Отправляем `POST` на адрес Supabase Auth с email и паролем в теле. В ответ приходит JSON с
`access_token` (пропуск на ~1 час), `refresh_token` (чтобы получить новый пропуск) и `expires_in`.

`synchronized` — метод может выполнять только один поток одновременно. Сеть мы вызываем из
фоновых потоков (см. 14.2), и два потока не должны одновременно менять `session`.

**Заголовки каждого запроса:**

```java
.header("apikey", publishableKey)                 // «я — приложение Kvit»
.header("Authorization", "Bearer " + token)       // «я — пользователь X» (только для данных)
```

Supabase требует оба: ключ проекта и токен пользователя. По токену база вычисляет `auth.uid()`.

**Автообновление токена:**

```java
if (Instant.now().plus(REFRESH_MARGIN).isAfter(session.expiresAt())) {
    refreshSession();
}
```

Если до истечения токена меньше минуты — получаем новый через `refresh_token`. Пользователь этого
не замечает. Если обновить не удалось — сессия сбрасывается и пользователь видит «Сессия истекла».

**Отправка и ошибки — метод `send`:**

1. Отправить запрос. Нет сети → `IOException` → понятное «Нет соединения с сервером».
2. Статус ≥ 400 → `toUserFriendlyError`: разбирает JSON ошибки и переводит коды в человеческий
   текст. Например, `invalid_credentials` → «Неверный email или пароль»; `PGRST205` (нет таблицы)
   → «Выполните supabase/schema.sql»; `P0001` (сработал наш триггер) → «База данных отклонила
   операцию: …».
3. Иначе разобрать JSON и вернуть.

Почему ошибки переводятся **здесь**, а не в экранах? Потому что только этот класс знает, что такое
HTTP-статус и коды Supabase. Экран получает готовое сообщение и просто показывает его.

**Почему `InterruptedException` обрабатывается особым образом:**

```java
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
    throw new DataAccessException(I18n.t("error.db.interrupted"), e);
}
```

Это правило Java: если поймал прерывание — восстанови флаг прерывания потока, чтобы тот, кто его
прервал, об этом узнал. Пустых `catch` в проекте нет вообще — требование задания.

### 8.2. `DebtRepository` и `PaymentRepository` — перевод между JSON и объектами

Supabase построен на **PostgREST**: каждая таблица автоматически становится адресом в сети.

| Действие | HTTP-запрос |
|---|---|
| Все долги (новые первыми) | `GET /rest/v1/debts?select=*&order=created_at.desc` |
| Долг с id=5 | `GET /rest/v1/debts?select=*&id=eq.5` |
| Создать | `POST /rest/v1/debts` + JSON в теле |
| Изменить id=5 | `PATCH /rest/v1/debts?id=eq.5` + JSON |
| Удалить id=5 | `DELETE /rest/v1/debts?id=eq.5` |

`eq.5` — синтаксис PostgREST: «равно 5». Заголовок `Prefer: return=representation` просит сервер
вернуть сохранённую строку — так мы сразу получаем `id` и `created_at`, которые выдала база.

**Преобразование «объект → JSON» (`toJson`):**

```java
json.put("title", debt.getTitle().trim());
json.put("original_amount", debt.getOriginalAmount());
json.put("due_date", debt.getDueDate() == null ? null : debt.getDueDate().toString());
json.put("status", debt.getStatus().name());
```

Мы **не отправляем** `id`, `user_id`, `created_at` — их ставит база. Дата отправляется строкой
`2026-10-25` (формат ISO, который понимает PostgreSQL). Статус — именем enum (`ACTIVE`).

**Преобразование «JSON → объект» (`toDebt`):**

```java
debt.setOriginalAmount(row.get("original_amount").decimalValue());
debt.setDueDate(row.hasNonNull("due_date") ? LocalDate.parse(row.get("due_date").asText()) : null);
debt.setStatus(DebtStatus.valueOf(row.get("status").asText()));
```

Почему вручную, а не «автоматически» (Jackson умеет сам заполнять объекты по аннотациям)?
Потому что так **видно** каждое поле и его тип, нет скрытой магии, а модель `Debt` не зависит от
формата JSON. Для 10 полей это 10 понятных строк.

**`singleRow`** — общий помощник: PostgREST всегда возвращает массив. Если массив пуст после
`PATCH` — значит, строки нет (или RLS её скрыл), и мы сообщаем «Запись не найдена».

**`blankToNull`** — пустое примечание сохраняем как `null`, а не как `""`: «нет значения» и
«пустая строка» — разные вещи, и в базе лучше хранить честное «нет значения».

**Почему в URL безопасно склеивать строку** (`"?id=eq." + debtId`)? Потому что `debtId` — число
(`long`). Текст пользователя (название, заметка) в URL никогда не попадает — только в тело JSON,
которое Jackson правильно экранирует. Поэтому инъекции невозможны.

### 8.3. `DataAccessException`

Своё исключение для ошибок данных. Наследуется от `RuntimeException` (непроверяемое), поэтому не
нужно писать `throws` в каждом методе. Сообщение **всегда написано для пользователя** — его можно
показать на экране без изменений.

## 9. Модели: `model`

### 9.1. `Debt` и `Payment` — обычные классы с get/set

```java
public class Debt {
    private Long id;
    private String title;
    private BigDecimal originalAmount;
    private LocalDate dueDate;
    private DebtStatus status = DebtStatus.ACTIVE;
    ...
}
```

Почему классы, а не `record`? Потому что их **заполняют по частям**: форма читает поле за полем,
репозиторий ставит значения из JSON, сервис меняет статус. Для изменяемых объектов удобнее класс.

Типы полей выбраны осознанно:

- `Long id` (с большой буквы) — может быть `null`: у нового, ещё не сохранённого долга id нет.
  По `id == null` сервис понимает «создать», иначе «обновить».
- `BigDecimal` — деньги (см. 6.1 про `numeric`).
- `LocalDate` — дата без времени (срок, дата платежа).
- `OffsetDateTime` — дата-время с часовым поясом (`created_at`).

### 9.2. Records: `DebtOverview`, `PaymentEntry`, `DashboardSummary` и др.

```java
public record DebtOverview(Debt debt, BigDecimal paid, BigDecimal remaining, boolean overdue) {}
```

`record` (Java 16+) — короткая запись неизменяемого класса-контейнера. Java сама создаёт
конструктор, геттеры `debt()`, `paid()`…, `equals`, `hashCode`, `toString`. Мы используем их для
**результатов расчётов**: они создаются один раз и дальше только читаются.

| Record | Что содержит | Кто создаёт |
|---|---|---|
| `DebtOverview` | долг + оплачено + остаток + просрочен ли | `DebtCalculator.overview` |
| `PaymentEntry` | платёж + название долга + кредитор | `DebtService.toEntries` |
| `DashboardSummary` | итоги для обзора | `DebtCalculator.summarize` |
| `DashboardData` | всё для экрана «Обзор» одним объектом | `DebtService.getDashboardData` |
| `ReportData`, `MonthTotal`, `CreditorTotal`, `StatusBreakdown`, `PayoffForecast` | данные отчётов | `ReportCalculator` |
| `CalendarData` | долги + платежи для календаря | `DebtService.getCalendarData` |
| `DateRange` | период дат | `CalendarView` |

Почему `DashboardData` — один объект, а не три вызова? Экран загружает данные в фоне **одним**
заданием и получает всё сразу. Иначе пришлось бы ждать три задания и следить, какое пришло первым.

### 9.3. `DebtStatus` — перечисление

```java
public enum DebtStatus {
    ACTIVE, PAID, CANCELLED;

    @Override
    public String toString() {
        return I18n.t("status." + name());
    }
}
```

`enum` гарантирует, что статус может быть только одним из трёх — опечатку `"ACTVE"` компилятор
не пропустит. `toString()` возвращает перевод, поэтому выпадающий список в форме сам показывает
«Активный» / «Белсенді» / «Active».

### 9.4. `DateRange` — компактный конструктор

```java
public record DateRange(LocalDate start, LocalDate end) {
    public DateRange {
        if (start.isAfter(end)) {
            LocalDate swap = start;
            start = end;
            end = swap;
        }
    }
}
```

«Компактный конструктор» record выполняется до присваивания полей. Здесь он гарантирует, что
начало никогда не позже конца: в календаре можно протянуть мышью и вправо, и влево, а период
всё равно будет правильным.

## 10. Бизнес-логика: `service`

Сердце программы. Ни одной строчки про окна или HTTP.

### 10.1. `DebtCalculator` — правила расчёта

```java
public BigDecimal remainingBalance(Debt debt, List<Payment> paymentsOfDebt) {
    return debt.getOriginalAmount().subtract(totalPaid(paymentsOfDebt));
}
```

**Остаток = сумма долга − сумма платежей.** Никаких процентов. Работа с `BigDecimal` — через
методы (`add`, `subtract`), потому что это объект, а не примитив: операторы `+`/`-` к нему не
применяются.

```java
public boolean isOverdue(Debt debt, List<Payment> paymentsOfDebt, LocalDate today) {
    if (debt.getStatus() == DebtStatus.CANCELLED || debt.getDueDate() == null) {
        return false;
    }
    return debt.getDueDate().isBefore(today)
            && remainingBalance(debt, paymentsOfDebt).signum() > 0;
}
```

**Просрочен** = срок уже прошёл **и** что-то осталось. Отменённый долг не может быть просрочен.

- `signum()` возвращает −1, 0 или 1 (знак числа). `signum() > 0` значит «больше нуля». Сравнивать
  `BigDecimal` через `equals` опасно: `new BigDecimal("1.0").equals(new BigDecimal("1.00"))` —
  **false** (разная точность). `signum` и `compareTo` сравнивают значения правильно.
- `today` передаётся параметром, а не берётся внутри через `LocalDate.now()`. Зачем? Чтобы в тестах
  подставить фиксированную дату. Иначе тест «просрочен ли долг со сроком 15 октября» давал бы
  разный результат в разные дни.

```java
public DebtStatus statusAfterPayments(Debt debt, List<Payment> paymentsOfDebt) {
    if (debt.getStatus() == DebtStatus.CANCELLED) return DebtStatus.CANCELLED;
    boolean fullyPaid = remainingBalance(debt, paymentsOfDebt).signum() <= 0;
    return fullyPaid ? DebtStatus.PAID : DebtStatus.ACTIVE;
}
```

Статус «Погашен» **не выбирает пользователь** — он вычисляется. Погасили до нуля → PAID. Удалили
платёж и остаток снова появился → обратно ACTIVE. Отмену может поставить и снять только пользователь.

`summarize` — проходит по всем долгам и складывает итоги (отменённые пропускаются, чтобы не
раздувать суммы). `needingAttention` — фильтрует активные долги с остатком, у которых срок прошёл
или наступит в ближайшие 14 дней, и сортирует по сроку (просроченные — первыми, у них дата раньше).

`paymentsOf` — выбирает из общего списка платежи одного долга. Почему не делаем отдельный запрос
в базу для каждого долга? Это была бы проблема «N+1 запросов»: 50 долгов = 51 запрос. Мы
загружаем **все** долги и **все** платежи двумя запросами и сопоставляем в памяти.

### 10.2. `DebtValidator` — проверка ввода

```java
public BigDecimal parseAmount(String text, String fieldName, boolean required) {
    String cleaned = text == null ? "" : text.replaceAll("[\\s\\u00A0\\u202F]", "").replace(',', '.');
    ...
    return new BigDecimal(cleaned);
}
```

Пользователь может ввести «1 500,50» (как пишут в Казахстане и России) или «1500.50». Мы убираем
пробелы (включая неразрывные, которые бывают при копировании из Word/Excel) и меняем запятую на
точку. Если текст всё равно не число — `ValidationException` с понятным сообщением.

`validateDebt` проверяет: название и кредитор не пустые и не длиннее 200 символов; сумма > 0, не
больше двух знаков после запятой (`scale() > 2`), не больше максимума `numeric(14,2)`; ставка 0–100;
сумма долга не меньше уже оплаченного.

`validatePayment` проверяет: выбран долг; сумма > 0 и не больше остатка; дата есть и не в будущем.

Ограничения в валидаторе **совпадают** с ограничениями в `schema.sql` (200 символов, 1000 для
заметок, 2 знака). Это намеренно: Java ловит ошибку раньше и показывает понятное сообщение, база —
страхует.

### 10.3. `DebtService` — «дирижёр»

Сервис не считает сам — он **координирует**: берёт данные из репозиториев, вызывает калькулятор
и валидатор, сохраняет результат. Разберём самый показательный метод — добавление платежа:

```java
public Payment addPayment(Payment payment) {
    if (payment.getDebtId() == null) {                                   // 1. долг выбран?
        throw new ValidationException(I18n.t("error.payment.noDebt"));
    }
    Debt debt = debtRepository.findById(payment.getDebtId());           // 2. свежий долг из базы
    if (debt.getStatus() == DebtStatus.CANCELLED) {                      // 3. не отменён?
        throw new ValidationException(I18n.t("error.payment.cancelledDebt"));
    }
    List<Payment> payments = new ArrayList<>(paymentRepository.findByDebtId(debt.getId()));
    validator.validatePayment(payment, calculator.remainingBalance(debt, payments), LocalDate.now()); // 4.

    Payment saved = paymentRepository.insert(payment);                   // 5. сохранить
    payments.add(saved);
    updateStatusIfChanged(debt, payments);                               // 6. стал «Погашен»?
    return saved;
}
```

Почему на шаге 2 долг читается **заново** из базы, хотя экран его уже показывал? Потому что за
это время данные могли измениться (например, в другом окне). Решение принимается по **актуальным**
данным.

`saveDebt` — одна функция и для создания, и для изменения: если `id == null` — `insert`, иначе
`update`. Перед сохранением пересчитывается статус (см. 10.1).

Методы `getDashboardData`, `getReportData`, `getCalendarData` — «собрать всё для экрана»: два
запроса (долги + платежи) и расчёты.

### 10.4. `ReportCalculator` — отчёты

**Платежи по месяцам:**

```java
Map<YearMonth, BigDecimal> totals = new LinkedHashMap<>();
for (int i = months - 1; i >= 0; i--) {
    totals.put(currentMonth.minusMonths(i), BigDecimal.ZERO);
}
```

Сначала создаём **все** 12 месяцев с нулём, потом раскладываем платежи. Без этого месяцы без
платежей просто пропали бы, и на графике не было бы «пустых» столбиков. `LinkedHashMap` сохраняет
порядок добавления — месяцы идут по порядку. `YearMonth` — тип Java «год+месяц», удобно
группировать.

**Кредиторы:** суммы складываются по имени кредитора, **приведённому к нижнему регистру без
пробелов по краям** — так «Kaspi Bank» и «kaspi bank » считаются одним кредитором. Если кредиторов
больше 6, хвост сворачивается в строку «Остальные» (на графике больше 6 полос уже не читаются).
Кредиторы с нулевым остатком убираются — график отвечает на вопрос «кому я должен».

**Прогноз:**

```
средний платёж = сумма платежей за последние 3 месяца / 3
месяцев до погашения = остаток / средний платёж, округлить ВВЕРХ
```

Округление вверх (`RoundingMode.CEILING`): если осталось 2,1 месяца платежей — понадобится 3
месяца, а не 2. Если платежей за 3 месяца не было — прогноз не строится (`null`), и экран честно
пишет «нет данных».

### 10.5. `PayoffPlanner` — «что если»

Два вопроса:

1. «Если платить X в месяц — когда погашу?» → `остаток / X`, вверх.
2. «Сколько платить, чтобы успеть к сроку?» → `остаток / число месяцев до срока` (минимум 1),
   округлено вверх **до целого тенге**: если округлить вниз, сумма платежей немного не дотянет.

### 10.6. `CsvExporter` — экспорт в Excel

Три особенности, без которых Excel открыл бы файл криво:

- разделитель `;` — так Excel ожидает CSV в русской/казахской Windows (запятая там — десятичный знак);
- в начале невидимый символ **BOM** (U+FEFF) — по нему Excel понимает, что файл в UTF-8, и
  кириллица не превращается в «кракозябры»;
- десятичная запятая в RU/KZ.

`escape` — если в значении есть `;`, кавычка или перенос строки, значение берётся в кавычки, а
внутренние кавычки удваиваются (`say "hi"` → `"say ""hi"""`). Это стандарт CSV (RFC 4180).

### 10.7. `AuthService` и `ValidationException`

`AuthService` проверяет email (простое регулярное выражение «что-то@что-то.что-то») и пароль
(не короче 8 символов, есть буква и цифра) **до** отправки на сервер, затем вызывает
`SupabaseClient`. `ValidationException` — «пользователь ввёл что-то не так»; его сообщение
показывается как есть.

Почему два своих исключения, а не одно? Они означают разное: `ValidationException` — «исправьте
ввод», `DataAccessException` — «проблема с сетью/сервером». Экран может по-разному на них
реагировать, а `BackgroundTask` знает, что оба сообщения уже понятны пользователю.

## 11. Настройки: `config`

### 11.1. `AppConfig` — откуда брать URL и ключ Supabase

Порядок: сначала файл `config.properties` рядом с программой, если там пусто — переменные
окружения `SUPABASE_URL` / `SUPABASE_PUBLISHABLE_KEY`. Переменные окружения удобны на сервере
сборки, файл — на компьютере разработчика.

Проверки: оба значения есть; URL начинается с `https://`; ключ **не секретный**.

```java
static boolean isSecretKey(String key) {
    if (key.startsWith("sb_secret_")) return true;
    String[] jwtParts = key.split("\\.");
    if (jwtParts.length == 3) {
        String payload = new String(Base64.getUrlDecoder().decode(jwtParts[1]), UTF_8);
        return payload.replace(" ", "").contains("\"role\":\"service_role\"");
    }
    return false;
}
```

Старые ключи Supabase — это **JWT**: три части через точку, средняя — JSON в кодировке Base64.
Мы раскодируем её и смотрим поле `role`. Если это `service_role` (ключ, который обходит RLS и видит
всё) — программа откажется запускаться. Это защита от самой опасной ошибки разработчика.

### 11.2. `UserSettings` — тема, язык, последний email

```java
private final Preferences preferences = Preferences.userRoot().node("kz/kvit");
```

`java.util.prefs.Preferences` — встроенный в Java механизм хранения маленьких настроек. На Windows
он пишет в реестр пользователя. Не нужно придумывать формат файла и место для него.

Хранится только: тема, язык, **последний email** (чтобы не вводить заново). Пароль — никогда.

Метод `parse` защищает от «мусора»: если в реестре окажется неизвестное значение (например, от
старой версии), берётся значение по умолчанию вместо падения.

## 12. Переводы: `i18n`

**i18n** — сокращение от «internationalization» (i + 18 букв + n).

### 12.1. Как устроено

Тексты лежат в трёх файлах с одинаковыми ключами:

```properties
# messages_ru.properties
nav.debts=Долги
due.inDays=Через {0} дн.
```

В коде вместо текста — ключ: `I18n.t("nav.debts")`. Класс `I18n` загружает нужный файл через
`ResourceBundle` и возвращает текст.

### 12.2. Важные детали `I18n`

```java
ResourceBundle.getBundle(BUNDLE, lang.getLocale(),
        ResourceBundle.Control.getNoFallbackControl(ResourceBundle.Control.FORMAT_PROPERTIES));
```

Почему `NoFallbackControl`? По умолчанию Java, не найдя, скажем, английский файл, берёт файл на
**языке компьютера**. На русской Windows выбор «English» показывал бы русский. Мы отключаем это:
запасной вариант — только базовый `messages.properties` (английский).

```java
return args.length == 0 ? text : new MessageFormat(text, locale()).format(args);
```

`MessageFormat` подставляет аргументы: `"Через {0} дн."` + `5` → `"Через 5 дн."`. В английском
используется выбор формы: `{0,choice,1#day|1<days}` → «1 day», «5 days». В русском мы пишем
сокращение «дн.» — так не нужны три формы (день/дня/дней). В казахском существительное после числа
не меняется — проблемы нет.

Если ключа нет — метод возвращает сам ключ и пишет предупреждение в консоль, а не падает: лучше
увидеть `nav.debts` на кнопке, чем закрывшуюся программу.

### 12.3. Сообщения об ошибках тоже переводятся

Даже в `DebtValidator` и `SupabaseClient` используется `I18n.t(...)`. Поэтому ошибка «Платёж
больше остатка» появится на выбранном языке.

### 12.4. Как проверяется

`I18nTest` убеждается, что во всех трёх файлах **одинаковый набор ключей** и что каждая строка —
корректный шаблон `MessageFormat`. Если кто-то добавит текст в русский файл и забудет казахский —
тест упадёт.

## 13. Основы JavaFX, без которых UI не понять

### 13.1. Stage, Scene, Node

- **Stage** — окно Windows (рамка, заголовок, кнопки свернуть/закрыть).
- **Scene** — содержимое окна. У сцены один **корневой** узел и список CSS-файлов.
- **Node** — любой элемент: кнопка, надпись, панель. Узлы вкладываются друг в друга — получается
  **дерево сцены**.

### 13.2. Панели раскладки (layout)

| Класс | Как раскладывает детей |
|---|---|
| `VBox` | столбиком сверху вниз |
| `HBox` | строкой слева направо |
| `StackPane` | друг на друга (слоями) — так мы кладём сетку *под* страницу, а диалог *над* ней |
| `BorderPane` | верх / центр / низ / лево / право — у главного окна: панель навигации сверху, страница в центре |
| `GridPane` | таблицей строк и столбцов — форма долга и сетка календаря |
| `ScrollPane` | добавляет прокрутку, если содержимое не помещается |

`HBox.setHgrow(node, Priority.ALWAYS)` — «этому элементу отдать всё свободное место по ширине».
`Ui.hSpacer()` — пустая растягивающаяся область, которая «расталкивает» элементы к краям.

### 13.3. Свойства и слушатели

Почти всё в JavaFX — **наблюдаемые свойства** (`textProperty()`, `widthProperty()`,
`selectedProperty()`…). К ним можно подписаться:

```java
searchField.textProperty().addListener((obs, oldText, text) -> applyFilter());
```

«Когда текст в поиске меняется — перефильтровать таблицу». Так поиск работает «на лету».

### 13.4. Главное правило: потоки

JavaFX рисует окно в **одном** потоке — *JavaFX Application Thread*. Если в этом потоке сделать
что-то долгое (сетевой запрос на 2 секунды), окно на 2 секунды **зависнет**: не будет реагировать
на клики и перерисовываться.

Поэтому: **всё сетевое — в фоновом потоке, всё про интерфейс — в потоке JavaFX**. Менять узлы из
фонового потока нельзя — это приводит к случайным ошибкам. Именно эту задачу решает
`BackgroundTask` (14.2).

### 13.5. CSS в JavaFX

Почти как CSS для сайтов, но свойства с префиксом `-fx-` (`-fx-background-color`,
`-fx-text-fill`). Узлу назначают класс: `label.getStyleClass().add("heading")`, а в CSS описывают
`.heading { ... }`. Особая возможность JavaFX — **looked-up colors**: переменные цвета,
объявленные в `.root`, которые используются везде (см. 15).

## 14. Интерфейс: каждый файл пакета `ui`

### 14.1. Общая схема экранов

```
App
├── LoginView          — экран входа (LoginHero — анимированная картинка слева)
└── MainView           — главное окно: панель навигации + текущая страница
    ├── DashboardView  — Обзор         (Ctrl+1)
    ├── DebtsView      — Долги         (Ctrl+2)
    ├── PaymentsView   — Платежи       (Ctrl+3)
    ├── ReportsView    — Отчёты        (Ctrl+4)
    ├── CalendarView   — Календарь     (Ctrl+5)
    └── SettingsView   — Настройки     (Ctrl+6)
    Диалоги поверх страниц (через ModalHost): DebtForm, PaymentForm, подтверждения
```

### 14.2. `BackgroundTask` — работа в фоне

```java
public static <T> void run(Callable<T> work, Consumer<T> onSuccess, Consumer<String> onError) {
    Task<T> task = new Task<>() {
        @Override
        protected T call() throws Exception {
            return work.call();           // выполняется в ФОНОВОМ потоке
        }
    };
    task.setOnSucceeded(event -> onSuccess.accept(task.getValue()));          // в потоке JavaFX
    task.setOnFailed(event -> onError.accept(userMessage(task.getException()))); // в потоке JavaFX
    Thread thread = new Thread(task, "background-task");
    thread.setDaemon(true);
    thread.start();
}
```

Использование на экранах всегда одинаковое:

```java
BackgroundTask.run(debtService::getDashboardData, this::showData, this::showError);
```

«Загрузи данные в фоне; получится — покажи; не получится — покажи ошибку». `Task` — класс JavaFX,
который сам переносит `onSucceeded`/`onFailed` обратно в поток интерфейса.

- `<T>` — **обобщённый тип** (generic): метод работает с любым результатом — списком долгов,
  `DashboardData`, `Payment`.
- `setDaemon(true)` — фоновый поток не мешает программе закрыться.
- `userMessage` — если ошибка «наша» (`ValidationException`, `DataAccessException`), её текст уже
  понятен пользователю. Иначе это неожиданная ошибка программы: печатаем подробности в консоль
  (для разработчика) и показываем общее сообщение.

### 14.3. `Page` — единственный интерфейс

```java
public interface Page {
    Node getRoot();
    default void refresh() {}      // F5
    default void createNew() {}    // Ctrl+N
    default void focusSearch() {}  // Ctrl+F
}
```

`MainView` не знает, какая страница открыта — `DebtsView` или `ReportsView`. Нажали F5 — он
вызывает `currentPage.refresh()`, и каждая страница сама решает, что это значит. Методы
`default` дают пустую реализацию: «Отчётам» не нужен поиск — они просто не переопределяют
`focusSearch()`. Это **полиморфизм** в чистом виде, и здесь интерфейс действительно нужен.

### 14.4. `MainView` — главное окно

**Навигация.** Каждый пункт создаётся методом `navItem` с **фабрикой страницы**:

```java
navItem(Icons.LIST, "nav.debts", () -> new DebtsView(debtService, modalHost, DebtsView.Filter.ALL));
```

`Supplier<Page>` — «функция, которая создаёт страницу». Страница создаётся **заново при каждом
открытии** — значит, данные всегда свежие, и не нужно следить за устаревшим состоянием.

`ToggleGroup` делает пункты меню взаимоисключающими (выбран только один). Строка
`item.setSelected(true)` в обработчике не даёт «снять» выделение повторным кликом.

**Горячие клавиши** — `addEventFilter(KeyEvent.KEY_PRESSED, ...)` на корне окна. *Фильтр*
(а не обработчик) перехватывает нажатие **до** того, как его получит, например, поле ввода. Пока
открыт диалог, клавиши страниц не работают (`if (modalHost.isModalOpen()) return;`).

**Переход к просроченным** — `openDebts(Filter.OVERDUE)` открывает «Долги» сразу с нужным фильтром.
Его вызывает кнопка «Показать» в баннере на обзоре.

**Автовыход через 15 минут** (`startIdleWatch`):

```java
modalHost.addEventFilter(InputEvent.ANY, event -> lastActivity = System.currentTimeMillis());
idleCheck = new Timeline(new KeyFrame(Duration.seconds(30), event -> {
    if (System.currentTimeMillis() - lastActivity > IDLE_MINUTES * 60_000) { ... выход ... }
}));
```

Любое движение мыши или нажатие клавиши обновляет «время последней активности». Раз в 30 секунд
`Timeline` (таймер JavaFX) проверяет, не прошло ли 15 минут. Таймер останавливается, когда окно
сменилось (`sceneProperty` стал `null`) — иначе после выхода он продолжал бы работать.

На узком окне email в правом верхнем углу скрывается (`visibleProperty().bind(...)`) — остаётся
иконка с подсказкой. Это **привязка (binding)**: видимость автоматически следует за шириной окна.

### 14.5. `LoginView` — экран входа

- Две вкладки «Вход / Регистрация» меняют заголовок, текст кнопки и подсказку о пароле.
- Кнопка «Войти» — `setDefaultButton(true)`: Enter в любом поле нажимает её.
- **Показать пароль:** `PasswordField` (точки) и обычный `TextField` лежат друг на друге в
  `StackPane`, их текст связан `bindBidirectional`. Кнопка-«глаз» просто показывает один и прячет
  другой. Связь двусторонняя, поэтому текст не теряется при переключении.
- Email подставляется из `UserSettings`, и курсор сразу встаёт в поле пароля.
- После успешного входа поле пароля очищается (пароль не висит в памяти интерфейса).
- Ошибка → `InfoBar` с сообщением + `Motion.shake(card)` (карточка «качает головой»).
- После регистрации Supabase требует подтвердить email: сервер не возвращает токен, и мы
  показываем «Проверьте почту».

### 14.6. `LoginHero` — анимация на экране входа

Это **украшение** с примерными цифрами (не данные пользователя). Части:

- **Кольцо погашения:** серый круг-дорожка + дуга `Arc`. `Timeline` за 1,8 с меняет длину дуги
  от 0 до −245° (68 %). Минус — потому что положительный угол в JavaFX рисуется против часовой
  стрелки. Слушатель длины дуги обновляет надпись «0% → 68%».
- **Плавающие карточки:** `TranslateTransition` двигает их вверх-вниз на 6 px бесконечно
  (`setAutoReverse(true)`, `INDEFINITE`).
- **Почему текст не дрожит:** узел, который двигается, рисуется из **кэша** —
  `setCache(true)`. Иначе JavaFX на каждом кадре заново рисовал бы буквы на дробных координатах
  пикселей, и они «прыгали» бы между пикселями.
- Ширина надписи процента фиксирована — иначе при смене «9%» на «10%» центр сдвигался бы.
- Сцена нарисована в координатах 520×360 и **масштабируется** под доступное место (`rescale`).
- Бесконечные анимации **останавливаются**, когда экран входа закрыт (слушатель `sceneProperty`),
  иначе они продолжали бы тратить процессор.

### 14.7. `DashboardView` — Обзор

- Пока данные грузятся — **скелетон** (серые плашки, которые мягко «пульсируют»). Это лучше
  крутящегося колеса: пользователь видит форму будущей страницы.
- Ошибка → `InfoBar` + кнопка «Повторить». Пусто → «Пока нет долгов» + кнопка «Новый долг».
  Требование задания: «useful empty/loading/error states».
- Приветствие зависит от времени суток (`LocalTime.now().getHour()`).
- Баннер «Просроченных долгов: N» появляется, только если такие есть.
- Полоса погашения анимированно заполняется при первом показе: ширину заполнения считаем как
  `ширина дорожки × доля`, а слушаем `widthProperty()` дорожки — потому что ширина известна
  только после раскладки окна.
- Строки «Требуют внимания» кликабельны и ведут в раздел «Долги».

### 14.8. `DebtsView` — Долги (самый сложный экран)

**Таблица с поиском, фильтром и сортировкой — три слоя списков:**

```java
ObservableList<DebtOverview> debts = FXCollections.observableArrayList();   // все загруженные
FilteredList<DebtOverview> filtered = new FilteredList<>(debts);             // + поиск и фильтр
SortedList<DebtOverview> sorted = new SortedList<>(filtered);                // + сортировка
sorted.comparatorProperty().bind(table.comparatorProperty());
table.setItems(sorted);
```

Мы не пересоздаём таблицу при поиске — меняем только **условие** (`filtered.setPredicate(...)`), и
JavaFX сама показывает подходящие строки. `SortedList` привязан к таблице: щёлкнули по заголовку
столбца — таблица сама меняет порядок.

Условие поиска — комбинация двух предикатов: `byText.and(byStatus)`. `Predicate` — функция «да/нет»
для каждой строки.

**Ячейки таблицы** (`setCellFactory`) — мы сами решаем, как выглядит ячейка: в столбце «Долг» —
две строки (название + кредитор), в «Статусе» — цветной значок. `updateItem` вызывается JavaFX при
каждом показе ячейки; важно обрабатывать `empty` (пустые строки внизу таблицы).

У столбцов свой `Comparator`: например, статус сортируется в логичном порядке «просрочен → активен
→ погашен → отменён», а не по алфавиту.

**Панель деталей (инспектор)** справа — показывает выбранный долг: остаток, полоса погашения,
детали, кнопки, **планировщик** и историю платежей. История грузится отдельным фоновым запросом
(`getPaymentsOfDebt`), чтобы таблица не ждала.

**Клавиши:** Delete — удалить (с подтверждением), Enter или двойной щелчок — изменить.

**Экспорт CSV:** `FileChooser` (стандартное окно «Сохранить как»), запись файла — в фоне.

### 14.9. `PaymentsView` — Платежи

Та же схема `FilteredList` + `SortedList`. Фильтр по периоду вычисляет дату начала
(`switch (period)`: начало месяца / минус 3 месяца / минус год). Над таблицей — итоги за выбранный
период (сумма, количество, средний платёж); они пересчитываются при каждом изменении фильтра.

### 14.10. `ReportsView` — Отчёты и свои графики

В JavaFX есть готовые графики (`BarChart`), но их сложно привести к единому стилю. Наши графики
собраны из обычных прямоугольников `Region`, и стиль задаётся CSS.

**Столбчатый график по месяцам:**

- Высота столбика = `сумма / максимум шкалы × 180 px`.
- **«Красивый» максимум шкалы** — `niceMax`: максимум округляется вверх до 1, 2 или 5 × 10ⁿ
  (89 000 → 100 000). Тогда подписи сетки — круглые числа (0 / 50K / 100K), а не 0 / 44 600 / 89 200.
- Подпись значения — **только у самого высокого столбика**, точные значения — во всплывающей
  подсказке при наведении. Цифра над каждым столбиком превратила бы график в кашу.
- Текущий месяц выделен более ярким цветом.

**Полосы по кредиторам** — длина полосы пропорциональна остатку, значение справа.

**Статусы** — одна полоса 100 %, разделённая на цветные сегменты с промежутками 2 px, и легенда
(цвет + название + количество + процент). Цвет **всегда** сопровождается подписью: человек с
нарушением цветовосприятия всё равно поймёт график.

### 14.11. `CalendarView` — Календарь

- Сетка 7×6: **всегда 6 недель**, чтобы высота не прыгала от месяца к месяцу. Неделя начинается
  с понедельника. Первый показанный день: `first.minusDays(first.getDayOfWeek().getValue() - 1)`
  — отступаем назад до понедельника.
- Данные раскладываются в `Map<LocalDate, List<...>>` — «день → события». Поиск событий дня
  становится мгновенным.
- **Выбор периода:** нажатие ставит «якорь» (`anchor`); `startFullDrag()` + `setOnMouseDragEntered`
  позволяют тянуть мышью по клеткам; Shift+щелчок расширяет период от якоря.
- Почему при выделении сетка **не перестраивается**, а меняются только CSS-классы
  (`updateSelectionStyles`)? Если удалить клетку, над которой сейчас идёт перетаскивание, жест
  оборвётся. Поэтому клетки остаются, меняется лишь их оформление.
- Месяц и год выбираются выпадающими списками. Флаг `updatingControls` защищает от «эха»: когда
  мы сами ставим значение в список, его слушатель не должен снова менять месяц.
- Готовые периоды и Esc — быстрый способ вернуться к сегодняшнему дню.

### 14.12. `SettingsView` и `SettingsControls`

`SettingsControls` — переключатели темы и языка, используются **в двух местах** (экран входа и
настройки), поэтому вынесены в отдельный класс. Выбор сохраняется в `UserSettings`, затем
вызывается `onChanged` — `App.reloadUi()` пересобирает экран.

`SettingsView` — карточки «Оформление», «Аккаунт», «Горячие клавиши», «О приложении».

### 14.13. `DebtForm` и `PaymentForm` — диалоги

- Открываются статическим методом `open(...)`, который создаёт объект формы и показывает его через
  `ModalHost`. Снаружи форма выглядит как одна команда: «открой форму, а когда сохранишь — сделай
  вот это» (`onSaved`).
- Проверка — **сразу в форме** (`validator.validateDebt`), чтобы ошибка появилась мгновенно, без
  ожидания сервера. Затем — сохранение в фоне через сервис (который проверит ещё раз).
- Кнопка «Сохранить» блокируется на время сохранения — защита от двойного нажатия.
- В форме долга статус можно выбрать только «Активный» или «Отменён»: «Погашен» ставится
  автоматически (10.1).
- В календаре платежа **будущие дни выключены** (`setDayCellFactory` + `setDisable`).
- `readDate` читает дату, введённую руками: стандартный `DatePicker` применяет её только после
  Enter, и без этого метода введённая дата терялась бы.
- Кнопка «Весь остаток» в платеже подставляет остаток долга.

### 14.14. `ModalHost` — диалоги внутри окна

Диалоги рисуются **внутри** главного окна, слоем поверх страницы (`StackPane`: страница →
затемнение → карточка → уведомления). Почему не отдельные окна Windows? Отдельное окно не
наследует наш CSS и тему так же легко, а «внутренний» диалог всегда выглядит как остальная
программа.

- `showModal` / `closeModal` — показать/закрыть; клик по затемнению и Esc закрывают.
- `confirm(...)` — универсальный вопрос «Удалить?» с кнопками «Отмена» / «Удалить».
- `toast(...)` — короткое уведомление в правом нижнем углу, исчезает через ~3 секунды
  (`PauseTransition` + `FadeTransition` в `SequentialTransition`).

### 14.16. `WindowsIntegration` — как Java вызывает Windows

JavaFX не умеет красить системный заголовок окна, и над тёмной программой висела бы белая полоса.
Мы вызываем функции Windows напрямую через **Foreign Function & Memory API** (стандартная часть
Java 22, без сторонних библиотек):

```java
MethodHandle findWindow = linker.downcallHandle(
        SymbolLookup.libraryLookup("user32", arena).find("FindWindowW").orElseThrow(),
        FunctionDescriptor.of(ValueLayout.ADDRESS, ValueLayout.ADDRESS, ValueLayout.ADDRESS));
```

1. Находим функцию `FindWindowW` в системной библиотеке `user32.dll` и описываем её параметры.
2. Находим наше окно по заголовку «Kvit».
3. Вызываем `DwmSetWindowAttribute` из `dwmapi.dll`: включаем тёмный режим заголовка и задаём цвет.

`Arena` — «участок памяти», который автоматически освобождается после `try`. Цвет в Windows
записывается как `0x00BBGGRR` (синий-зелёный-красный — в обратном порядке).

Это **косметика**: любая ошибка ловится, пишется в консоль, а программа работает дальше со
стандартным заголовком. Флаг `--enable-native-access=ALL-UNNAMED` в `pom.xml` разрешает такие
вызовы без предупреждений.

## 15. Дизайн-система: CSS и темы

### 15.1. Токены цвета

В начале `styles.css`:

```css
.root {
    -canvas: #18181a;
    -text-strong: #f2f2f3;
    -accent: #6a4ee0;
    -danger: #e5735a;
    -edge: rgba(255, 255, 255, 0.08);
    ...
}
```

Это **looked-up colors** JavaFX — переменные. Ниже везде используются **только имена**:

```css
.label { -fx-text-fill: -text; }
.badge.danger { -fx-text-fill: -danger; }
```

Плюсы: цвет меняется в одном месте; невозможно случайно взять «почти такой же» оттенок; светлая
тема — это просто другой набор значений тех же переменных.

### 15.2. Правила дизайна, которые соблюдаются

- **Один акцент** — фиолетовый, только на главной кнопке формы («Войти», «Сохранить»). Если
  акцент везде, он перестаёт выделять главное.
- Цвета статусов **со смыслом**: красный — просрочено, бирюзовый — оплачено/погашено,
  серо-голубой — активно, серый — отменено. И всегда рядом с цветом — текст.
- Деньги в таблицах выровнены по правому краю — разряды стоят друг под другом и легко сравниваются.
- Плоские панели с тонкой границей, без свечений и градиентного текста — спокойный рабочий вид.

### 15.3. Почему светлая тема — отдельный файл

Выпадающие списки, календарь `DatePicker` и подсказки открываются в **отдельных маленьких окнах**
(popup). Если бы мы включали светлую тему классом на корневом узле главного окна, эти popup-окна
его бы не получили и остались тёмными. Список CSS-файлов сцены popup-окна **наследуют** —
поэтому светлые токены лежат в отдельном `theme-light.css`, который просто добавляется в сцену.

### 15.4. Шрифты и значки

Используется *Segoe UI* (системный шрифт Windows) и *Segoe Fluent Icons* для значков. Вариативный
*Segoe UI Variable* JavaFX не умеет загружать — это проверено, поэтому выбран обычный Segoe UI.

## 16. Тесты

Запуск: `.\mvnw.cmd test`. Тесты лежат в `src/test/java` и повторяют структуру пакетов.

| Тест | Что проверяет |
|---|---|
| `DebtCalculatorTest` | остаток, просрочка (включая «срок сегодня — ещё не просрочен»), смена статуса, итоги, «требуют внимания» |
| `DebtValidatorTest` | разбор «1 500,50», отказ на «abc», пустые поля, лишние знаки, переплату, дату в будущем |
| `ReportCalculatorTest` | месяцы с нулями, объединение кредиторов без учёта регистра, «Остальные», статусы, прогноз |
| `PayoffPlannerTest` | округление месяцев вверх, платёж к сроку до целого тенге |
| `CsvExporterTest` | экранирование `;` и кавычек, BOM, десятичная запятая/точка |
| `AuthServiceTest` | формат email, требования к паролю |
| `AppConfigTest` | секретные ключи распознаются, публичные — нет |
| `I18nTest` | одинаковые ключи в трёх языках, корректные шаблоны, переключение языка |
| `DateRangeTest` | порядок кликов не важен, границы включены, длина периода |

Пример — как читать тест:

```java
@Test
void debtIsNotOverdueOnDueDateItself() {
    Debt debt = debt(1L, "1000.00", TODAY, DebtStatus.ACTIVE);   // срок — сегодня
    assertFalse(calculator.isOverdue(debt, List.of(), TODAY));    // ещё НЕ просрочен
}
```

Название теста — это **правило**, записанное словами. `TODAY` — фиксированная дата
(25.10.2026), поэтому тест даёт одинаковый результат в любой день.

Почему тестируются именно сервисы, а не экраны? Ошибка в расчёте денег — самая дорогая, и
правила должны быть проверены автоматически. Экраны проверяются глазами (запуском программы).
И именно благодаря слоям (раздел 2) сервисы можно тестировать без окна и без сети.

## 17. Сквозные сценарии

### 17.1. Пользователь входит

1. `LoginView.signIn()` берёт email и пароль из полей, блокирует форму, показывает «Входим…».
2. `BackgroundTask.run(...)` — дальше в фоновом потоке:
3. `AuthService.signIn` проверяет формат email и что пароль не пустой.
4. `SupabaseClient.signIn` → `POST /auth/v1/token?grant_type=password`.
5. Supabase проверяет пароль и возвращает токены → сохраняются в `session` (в памяти).
6. Обратно в потоке JavaFX: email сохраняется в настройках, поле пароля очищается,
   вызывается `onSignedIn` → `App.showMain(0)` → открывается «Обзор».
7. Ошибка на любом шаге → сообщение в `InfoBar`, карточка встряхивается.

### 17.2. Пользователь вносит платёж

1. «Внести платёж» → `PaymentForm.open` в фоне загружает долги и оставляет **активные с остатком**.
2. Форма показывает список долгов и остаток выбранного.
3. «Сохранить» → форма разбирает сумму (`parseAmount`), дату (`readDate`) и сразу проверяет
   (`validatePayment`). Ошибка — видна мгновенно.
4. В фоне: `DebtService.addPayment` → читает **свежий** долг и платежи → снова проверяет → `insert`.
5. HTTP: `POST /rest/v1/payments` с `Authorization: Bearer <токен>`.
6. В базе: RLS проверяет, что долг принадлежит пользователю; триггер блокирует строку долга и
   проверяет, что платёж не больше остатка; `check` — что сумма > 0.
7. Если остаток стал 0 → `updateStatus(PAID)` (`PATCH /rest/v1/debts?id=eq.N`).
8. В потоке JavaFX: диалог закрывается, всплывает «Платёж 29 200 ₸ внесён», страница перезагружается.

### 17.3. Пользователь меняет язык на казахский

1. Щелчок «KZ» в `SettingsControls` → `settings.setLanguage(KK)` (запись в реестр).
2. `onChanged` → `App.reloadUi()` → `I18n.setLanguage(KK)` загружает `messages_kk.properties`.
3. `showMain(текущий раздел)` создаёт экран заново — все `I18n.t(...)` возвращают казахские тексты,
   `Formats` пишет даты по-казахски («25 қазан 2026»).

### 17.4. Пользователь отошёл от компьютера

1. 15 минут нет ни одного движения мыши/нажатия — `lastActivity` не обновлялся.
2. Таймер `idleCheck` это замечает, останавливается, в фоне вызывает `authService.signOut()`
   (токен на сервере аннулируется, в памяти — стирается).
3. `onSignedOut.accept(сообщение)` → `App.showLogin(сообщение)` → экран входа с плашкой
   «Вы были неактивны 15 минут…».

## 18. Вопросы на защите и ответы

**— Почему вы не подключаетесь к базе через JDBC?**
Тогда пароль базы пришлось бы хранить в программе, а программу можно разобрать и достать его.
Мы используем Supabase Auth: пользователь входит своим паролем, получает временный токен, а база
по правилам RLS отдаёт только его строки. В программе только открытый ключ, который без входа
ничего не даёт.

**— Что такое RLS?**
Row Level Security — правила на уровне строк. База сама добавляет к каждому запросу условие
«`user_id` = пользователь из токена». Даже если в коде программы будет ошибка, чужие данные
вернуться не могут.

**— Почему деньги в `BigDecimal`, а не в `double`?**
`double` хранит числа в двоичном виде и не может точно представить 0,1. `0.1 + 0.2` в `double`
равно `0.30000000000000004`. В деньгах это ошибки в копейках/тиынах. `BigDecimal` считает в
десятичной системе точно. В базе ему соответствует `numeric(14, 2)`.

**— Почему остаток не хранится в базе?**
Он полностью вычисляется из платежей. Если хранить, нужно синхронизировать его при каждом
добавлении/удалении платежа, и любая ошибка даст неверный остаток. «Единый источник правды» —
таблица платежей.

**— Зачем проверки и в Java, и в базе?**
В Java — для удобства: понятное сообщение сразу, без запроса на сервер. В базе — для гарантии:
к API можно обратиться в обход программы, и тогда защищают только `check`, триггеры и RLS.

**— Что будет, если два платежа придут одновременно?**
Триггер берёт блокировку строки долга (`select ... for update`). Второй платёж ждёт окончания
первого и проверяет остаток уже с его учётом. Переплаты не будет.

**— Зачем слои? Это же лишние файлы.**
Чтобы правила можно было тестировать без окна и сети, чтобы замена базы затронула только
repository, и чтобы каждый класс отвечал за одно. В проекте 45 автоматических тестов — без слоёв
их было бы невозможно написать.

**— Почему окно не зависает при загрузке?**
Все сетевые операции выполняются в фоновом потоке через `BackgroundTask` (на основе `Task`
JavaFX), а результат возвращается в поток интерфейса. Поток интерфейса никогда не ждёт сеть.

**— Как устроены переводы?**
Три файла `messages*.properties` с одинаковыми ключами. В коде — только ключи
(`I18n.t("nav.debts")`). Смена языка пересобирает экран. Тест проверяет, что ни один ключ не
забыт ни в одном языке.

**— Почему «Погашен» нельзя выбрать вручную?**
Потому что это не мнение, а факт: долг погашен, когда платежи покрыли сумму. Статус вычисляется
автоматически, и пользователь не может случайно пометить неоплаченный долг погашенным.

**— Как работает прогноз погашения? Это точно?**
Средний платёж за 3 последних месяца; остаток делится на него и округляется вверх. Это оценка:
проценты и изменения графика не учитываются, и программа прямо пишет об этом под прогнозом.

**— Что происходит с данными при удалении долга?**
Внешний ключ `on delete cascade` удаляет все платежи этого долга. Перед удалением программа
спрашивает подтверждение.

**— Где хранятся тема и язык?**
В `java.util.prefs.Preferences` — на Windows это ветка реестра текущего пользователя.

**— Почему нет FXML?**
Экраны динамические и строятся из данных; в коде это проще и нагляднее. Всё описание экрана —
в одном файле.

**— Как вы обеспечили безопасность пароля?**
Пароль не сохраняется нигде; после входа поле очищается; передаётся только по HTTPS на сервер
Supabase, где хранится в виде хэша. Токены — только в памяти. Автовыход через 15 минут.

## 19. Как расширять проект

**Добавить поле долга (например, «категория»):**

1. `schema.sql`: `alter table public.debts add column category text check (char_length(category) <= 50);`
2. `Debt.java`: поле + геттер/сеттер.
3. `DebtRepository`: строка в `toJson` и в `toDebt`.
4. `DebtValidator`: проверка длины (такая же, как в базе).
5. `DebtForm`: поле ввода + чтение в `readForm`.
6. Переводы: ключ `form.category` во **все три** файла (иначе упадёт `I18nTest`).
7. Тест на новое правило, если оно есть.

**Добавить язык (например, узбекский):**

1. В `I18n.Language` — `UZ("uz", "Oʻzbekcha", "UZ")`.
2. Файл `messages_uz.properties` со всеми ключами.
3. В `I18nTest` — добавить файл в проверку.

**Добавить раздел:**

1. Класс `XxxView implements Page`.
2. В `MainView.build()` — `navItem(иконка, "nav.xxx", () -> new XxxView(...))`.
3. Горячая клавиша в `handleShortcut`, переводы `nav.xxx`.

## 20. Словарь терминов

| Термин | Объяснение |
|---|---|
| **API** | Набор «адресов», через которые одна программа просит другую что-то сделать |
| **REST** | Стиль API поверх HTTP: GET — прочитать, POST — создать, PATCH — изменить, DELETE — удалить |
| **JSON** | Текстовый формат данных: `{"title": "Кредит", "amount": 1500.50}` |
| **Токен (JWT)** | Временный «пропуск», подписанный сервером; подтверждает, кто вы |
| **RLS** | Row Level Security — правила, какие строки видит пользователь |
| **Триггер** | Функция в базе, которая срабатывает автоматически при изменении строки |
| **Внешний ключ** | Ссылка из одной таблицы на строку другой (платёж → долг) |
| **Транзакция** | Группа изменений «всё или ничего» |
| **Состояние гонки** | Ошибка, когда результат зависит от того, кто «успел первым» |
| **Слой (layer)** | Группа классов с одной обязанностью (ui / service / repository) |
| **Модель** | Класс, описывающий данные (долг, платёж) |
| **Record** | Короткая запись неизменяемого класса-контейнера в Java 16+ |
| **Enum** | Тип с фиксированным набором значений |
| **Лямбда** | Короткая анонимная функция: `x -> x * 2` |
| **Callback** | Функция, которую передают, чтобы её вызвали позже («когда сохранишь — сделай это») |
| **Generic `<T>`** | «Любой тип» — метод работает с разными типами данных |
| **Поток (thread)** | Отдельная «линия» выполнения программы; интерфейс JavaFX — в своём потоке |
| **Binding** | Привязка свойства к другому: изменилось одно — изменилось и второе |
| **Looked-up color** | Переменная цвета в CSS JavaFX, объявленная в `.root` |
| **i18n** | Интернационализация — поддержка нескольких языков |
| **BOM** | Невидимый символ в начале файла, сообщающий кодировку UTF-8 |
| **Maven Wrapper** | Скрипт `mvnw`, который сам скачивает нужную версию Maven |
| **`.gitignore`** | Список файлов, которые Git не отправляет в репозиторий |
